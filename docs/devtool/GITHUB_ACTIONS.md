# Cinderbox Companion — GitHub Actions via Devtool

This repository uses Devtool's native **ACTIONS-05 Android provider**, not a
hand-written API client. The dispatchable workflow is
`.github/workflows/devtool-android-build.yml`, with exactly the input names
`project_dir`, `module`, `variant`, and `format` expected by Devtool.

The remote job performs the checked-in M0/M1 source security contract,
Android JVM unit tests, Android Lint, and debug APK assembly. It checks the
APK structure, records SHA-256 and source-commit identity, and publishes
exactly one APK plus nonsecret evidence to the GitHub Actions artifact.
Linux CI uses JDK 17 and Android SDK 35; Termux does **not** need a local
Gradle/Android compiler to dispatch and monitor a remote build.

## One-time registration on GitHub's default branch

GitHub only enables `workflow_dispatch` when the workflow file exists on
the **default branch** (currently `master`). Therefore adding this file to
`security/m0-m1-hardening` alone is **not sufficient** for the first
`devtool actions android run`. Commit/push the identical workflow file to
`master` too. The security source changes remain confined to their branch.

From a clean checkout with both branches available, after applying the patch
to and committing the security branch:

```sh
git fetch origin
git switch master
git pull --ff-only origin master
git restore --source security/m0-m1-hardening -- .github/workflows/devtool-android-build.yml
git add .github/workflows/devtool-android-build.yml
git commit -m 'ci: register Devtool Android Actions workflow'
git push origin master
git switch security/m0-m1-hardening
```

Workflow registration can take a short time to appear in GitHub's Actions
interface. Make sure GitHub Actions is enabled for the fork. On an Actions
permissions issue, use a token with repository Actions **read/write** scope
(or `gh auth login` plus authorization for this repository). SSH transport
is fine for Git push but **does not authenticate the GitHub REST dispatch**.

## Plan and dispatch from Termux

```sh
cd "$HOME/Code/Cinderbox-Companion"
git switch security/m0-m1-hardening
git status --short                    # MUST be clean
devtool -r "$PWD" actions android discover --project-dir . --json
devtool -r "$PWD" actions android plan \
  --project-dir . --module app --variant debug --format apk \
  --ref security/m0-m1-hardening --json
devtool -r "$PWD" actions android run \
  --project-dir . --module app --variant debug --format apk \
  --ref security/m0-m1-hardening --yes --json
```

Devtool will refuse dispatch if local Git has uncommitted/untracked changes
or `HEAD` differs from the selected GitHub ref. It records a **request ID**
before dispatching, so a network interruption does not cause an automatic
duplicate GitHub Actions run. Preserve that request ID.

## Watch and retrieve the validated debug package

Once the dispatch returns its request/run ID:

```sh
devtool -r "$PWD" actions watch --request-id REQUEST_ID
devtool -r "$PWD" actions artifacts --run-id RUN_ID --json
devtool -r "$PWD" actions android collect \
  --run-id RUN_ID --artifact-id ARTIFACT_ID \
  --format apk --variant debug --expected-package com.sdvsync \
  --download --json
```

Do not guess `RUN_ID` or `ARTIFACT_ID`; copy the exact values from Devtool's
response. `actions android collect` requires `apksigner` and `aapt`/`aapt2`
available locally and checks the successful `workflow_dispatch` run,
artifact digest, manifest, and APK signing before materializing the APK under
`.devtool/artifacts/android-verified/`.

## Security and release boundary

- The workflow accepts **only debug APK** requests. It never consumes a
  release keystore or secrets, and has `contents: read` permission.
- Android's debug keystore is generated by GitHub's runner, so APKs from
  different runs may use different signing keys; this is not a stable
  upgrade path for an existing installed release.
- This is a **debug artifact**, not a reproducible, trusted, or signed
  production release. The `qualified_release` status remains false.
- No automatic app installation or on-device testing happens in CI.
- For future production releases, use a separately qualified signing lane
  with stable identity and verified source provenance; don't silently turn
  this debug workflow into an unattended release signer.
